PROPOSED APPROACH: Dual-Horizon Predictive Batching with Pre-Emptive Battery Cycling

Core Philosophy: Shift from reactive regime-following to proactive cost minimization by:
- Building long-term ("costmap") understanding of recurring low-price windows
- Pre-positioning battery 18-36 hours before predicted peak windows
- Batching compute in two tiers: emergency (hard deadlines <6h away) and scheduled (flexible deadlines 6-30h away)
- Smoothing load to flatten price response curve

Key Implementation Changes:

1. COSTMAP LEARNING (New module)
   - Compute rolling 7-day price percentiles by hour-of-week (168 hourly buckets)
   - Identify "golden hours" where p25 price falls below mean - 0.5*stdev
   - Track recurrence pattern (how often these windows repeat weekly)
   - Use this as prior for next week's schedule prediction

   Expected impact: Reduces peak price sensitivity by enabling pre-planned compute scheduling rather than reactive serving

2. BATTERY PRE-POSITIONING STRATEGY (Replace current reactive model)
   Current: Charge when regime==0 (opportunistic), discharge when regime>=2 (reactive)
   Proposed:
   - If next 24-48h contains predicted high-cost windows (p75+), begin charging now if SOC < 70%
   - Build toward 80% SOC by 4 hours before predicted peak, then hold
   - During peak window, discharge only to soften load spikes (discharge at 60% power, not 90%)
   - This creates "battery buffer" for unexpected peaks rather than energy arbitrage

   New threshold logic:
   ```

   if peak_window_hours and soc < 70 and current_regime <= 1:
   ```

   Expected impact: Increases battery utilization from 17.5% → 45-55% by deliberate cycling; reduces peak demand surges

3. COMPUTE BATCHING REFINEMENT (Replace uniform backlog serving)
   Current: Serve all arriving flex + fraction of backlog based on regime + urgency
   Proposed: Stratify backlog into priority tiers

   Tier 1 - EMERGENCY: oldest_backlog_age > 24h (deadline imminent)
   → Serve immediately at baseline rates (cannot defer further)
   → Budget: cap at arriving_flex_mw + backlog_mwh * 0.40

   Tier 2 - SCHEDULED: oldest_backlog_age 6-24h (flexible window)
   → Serve only during golden hours (lowest p25 windows in rolling costmap)
   → If in golden hour: serve at backlog_mwh * 0.95
   → If not in golden hour: serve only arriving_flex_mw
   → Budget: hold for next golden window within deadline

   Tier 3 - FLEXIBLE: arriving_flex_mw with <6h deadline
   → Serve immediately at full rate (hard SLA)

   Fallback: If no golden hour appears before deadline, linearly interpolate serving over final 6 hours

   Expected impact: Reduces demand-side price shocks by smoothing compute arrivals; targets lowest-cost windows; should reduce peak impact from 196.2 to ~120-140 $/MWh

4. REGIME THRESHOLD ADAPTATION (Reduce binary logic brittleness)
   Current: Hard thresholds at p25, p50, p75 classify all prices into 4 buckets
   Proposed: Soft regime scores using sigmoid transitions

   ```
   regime_score = sigmoid((current_price - p50) / (p75 - p25))
   # regime_score in [0, 1]: 0=low, 1=peak
   # Use for smooth interpolation between decisions, not hard classification

   def sigmoid(x):
       return 1 / (1 + exp(-x))
   ```

   Apply to battery aggressiveness:
   - regime_score 0.0-0.2: charge if below 80% SOC
   - regime_score 0.2-0.6: hold current SOC
   - regime_score 0.6-1.0: discharge proportionally (discharge_power = max_power * (regime_score - 0.6) / 0.4)

   Expected impact: Eliminates oscillation at regime boundaries (e.g., price at p75±1 no longer flips policy); smoother, more stable decisions

5. SHORTENED BATCH_WINDOW for Tighter Forecasting
